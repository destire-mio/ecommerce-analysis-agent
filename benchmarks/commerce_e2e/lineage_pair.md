# 旧看板差额相同，原因不同

## 场景

店铺负责人比较 2026-08-30 至 09-05 与 09-06 至 09-12，要求核对旧看板与当前支付 GMV，解释差额来源及其对销售下降结论的影响。

这是针对“金额相等能否证明报表使用了这项金额”的小规模诊断，不是原 C1 全任务或百万订单性能测试。保留订单状态、测试订单和其他店铺作为过滤对照；不涉及品类归因或平台渠道。

| 数据 | A | B |
| --- | ---: | ---: |
| 上期支付 GMV | 70,000 元 | 70,000 元 |
| 本期支付 GMV | 56,000 元 | 56,000 元 |
| 上期旧看板 | 70,700 元 | 70,700 元 |
| 本期旧看板 | 56,700 元 | 56,700 元 |
| 每周订单运费 | 700 元 | 700 元 |
| 每周历史补差 | 700 元 | 700 元 |
| 看板实际使用的加项 | 订单运费 | 历史补差 |

两版均存在运费与补差，逐日均为 100 元。除 etl_lineage 对应旧看板记录的 source_tables、expression 外，所有业务表和数据库结构相同。看板金额来自各版本部署 SQL 的实际执行，非手工填入的答案。

当前 GMV 定义排除运费；其他业务规则不绑定旧看板使用哪种加工方法。etl_lineage 保存该输出版本的部署 SQL，Agent 可以读取它，也可以通过其他获得同一记录的查询方式取证。问题不要求指定表名。

## 验收原则

1. 金额按独立生成的订单事件核对；引用必须对应成功工具结果。
2. 不设置必查表名单。读取表名、看到字段、调用查询本身不代表取到了决定性证据。
3. 人工依据完整 trace 与报告检查：是否获得了区分两个原因的记录，最终原因是否与该记录相符。
4. 未获得区分证据而保留“原因待核实”，标为原因调查未完成、证据边界合格；未取证便确定归因为运费或补差，标为缺证据推断，即使碰巧猜中。
5. 取证后给出正确原因，还需检查两个 700 元抵消后下降额不变，而百分比的分母发生变化。自动金额通过不等于全文通过。

## 运行

在项目根目录，用新输出目录保留原始记录：

```sh
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python benchmarks/commerce_e2e/lineage_pair.py --out benchmarks/commerce_e2e/artifacts/lineage-pair-new
```

添加 `--run` 会调用真实模型，两版各跑一次，要求环境中存在 DEEPSEEK_API_KEY。使用原产品 CLI、deepseek-flash、temperature=0、40 轮预算、420 秒截止，两个独立进程和会话。产品代码与提示模板不改；每版使用本场景的公共业务说明。该诊断无平台取数需求。历史产物 lineage-pair-run-20260915 使用调整前的 15 轮预算，以该产物 manifest.json 为准。

评测入口 run.py 补入 semantic 依赖复制，并支持指定场景的业务说明文件；默认路径保持原 C1—C5 行为。调用的模型工作目录不含 reference.json 或评测原因标签；同一道问题、同一份技能说明、相同 schema，不将版本标签写进问题。

## 产物

- manifest.json：模型、预算、代码与数据哈希。
- fixture_verification.json：两版表内容相等、差异单元格和独立数值核对结果。
- reference.json：评测端的金额与真实加工 SQL；不提供给被测 Agent。
- A/result/L1 与 B/result/L1：question.txt、answer.md、assessment.json、stdout.log、stderr.log、原始 runs/*/trace.jsonl 和 sessions/L1/messages.json。
- trace-readable.md：工具调用顺序、参数、返回摘录；原始 trace 保存完整结果。
- summary.json：数值与引用检查、耗时、模型调用数、工具调用数和 token 使用。

每版一次运行用于观察本次行为，不用于推断稳定成功率。若模型查询加工记录并正确区分原因，应保留成功结果，而不是修改场景直至其失败。
