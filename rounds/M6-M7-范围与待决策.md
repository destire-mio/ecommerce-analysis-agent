# M6 范围与待决策（产品承载 / 第 4 轮）

> 状态：**设计未讨论，先出范围 + 待决策**。定了再写成任务书（同 M4/A2 规格）。
> 硬约束（AGENTS.md 第 4 轮）：**不新增业务功能**，只把 Runtime 放进真实产品。

## 目标
用户能真正用起来：提问 → 看到结论 + 查看依据（证据）。

## 已具备（Runtime 侧）
`agent_loop.run_agent(question, bench, db_id, session_id)` 返回 `{status, answer, answer_full, executions, session_id, run_id}`——**这就是可被 UI 调用的 Runtime 入口**。证据在 `answer_full` 的 `###EVIDENCE###` 之后 + `executions`（Qn 账本）。

## 待决策（需先讨论）

| # | 决策 | 选项 | 我的倾向 |
|---|---|---|---|
| X1 | UI 技术栈 | a) Python 标准库 `http.server` + 单 HTML 页（零依赖）<br>b) Flask/FastAPI<br>c) Electron/Tauri 桌面 | **a**（零依赖，最快冒烟；桌面打包留后） |
| X2 | IPC 形态 | a) HTTP（本地服务）<br>b) 子进程 stdin/stdout协议 | **a**（UI→HTTP→Runtime 即"IPC"，链路清晰） |
| X3 | "查看依据"怎么呈现 | a) 折叠块展示 `answer_full` 的证据段<br>b) 结构化列表（Qn/工具/SQL/结果）从 `executions` 渲染 | **b**（结构化，可审计） |
| X4 | 打包冒烟怎么算 | a) 启动脚本 + 打开浏览器 + 自动跑一题断言<br>b) 真打包（PyInstaller/桌面壳） | **a**（第 4 轮"冒烟"即可，真打包 M6.5） |
| X5 | 会话/多轮 | 复用现有 `--session`（同会话追问）；UI 用 session_id 维持 | 复用 |

## 拟定范围（待确认后细化）
1. 本地 HTTP 服务：`POST /ask {question, session_id?}` → `run_agent` → 返回结论+依据
2. 单页前端：输入框 + 结论区 + "查看依据"折叠/结构化区 + （若 M5 完成）图表渲染
3. 启动脚本 `app.py`（起服务+开浏览器）
4. 冒烟脚本 `tools/run_smoke.py`：起服务→POST 一题（如"近7天商品支付金额"）→断言返回含 800000 且 status=ok
5. 发布门禁：`tools/run_release_gate.py` = 全套确定性验收 + 各 golden + 冒烟 全绿才算过

## 验收（定型后写死）
- 冒烟：提问返回结论 + 依据可取（结构含 Qn）
- 发布门禁脚本跑出全绿清单

## 预估：一天~一天半（HTTP/前端链路未踩过；打包留后）

# M7 范围与待决策（治理与运维 S6~S8）

> 状态：**设计未讨论**。演示可只做"权限 + 审计"最小版。

## 目标：可管、可控、可运维

## 分项与待决策

### S8 权限（最该先做）
- **租户隔离**：现在 `shop_id=1` **写死在 ref_sql 里**。应改为**引擎注入**（access scope 与业务口径分离——评审强调的三类条件之一）。待决策：租户从哪来（会话/请求参数/配置）？
- **列级权限**：mdl.yaml 列声明加 `expose_to`/`hidden`；材料包与展开时过滤。待决策：权限模型（按角色？按请求？）
- **审计**：每次 run 落一条审计（谁/何时/问了什么/取了哪些数）。现有 `runs/*/trace.jsonl` 可扩展为审计源。

### S7 治理
- **血缘**：metric→measure→model→物理表，从 mdl.yaml 推导出 lineage 图（可导出）
- **指标版本/审批**：mdl.yaml metric 已有 version；加 `status: approved|draft`，draft 不进材料包
- **schema 变更影响**：改 mdl.yaml/schema 时列出受影响指标（可做简单 diff 检查）

### S6 运维
- **成本预算**：token 记账已有（trace 里 `llm` 事件）；加"每会话 token 上限"门禁
- **监控/重跑**：runs/ 已是证据库；加失败重跑脚本
- **缓存/预聚合**：按需，暂不做（评审也说不必）

## 验收（定型后写死）
- 权限：带不同租户/角色请求，ref_sql 注入正确、隐藏列不可见
- 审计：一次提问产生可查询的审计记录
- 血缘：导出 metric→表 的 lineage

## 预估：一两天（最小版=租户注入 + 审计；列级权限/血缘/版本按需）

## 需先讨论的顺序
S8 租户注入（改 ref_sql 注入方式，影响语义层）→ S8 审计 → S7 版本/血缘 → S6 预算。**建议 S8 先讨论**，因为它动的是语义层的口径注入方式。
